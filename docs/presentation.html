1 · Executive summary

The whole ticket-to-MR loop, in a couple of clicks

Loopline is a working VS Code extension that automates the repetitive, error-prone steps between picking up a Jira ticket and opening a GitLab merge request. Today those steps are done by hand, inconsistently, dozens of times a week per developer. Loopline turns pick ticket → branch → commit → push → merge request → ticket status into a couple of clicks, with naming and commit conventions enforced automatically, surfaced in a dedicated sidebar that also tracks its own impact.

2 · Problem statement

Every ticket needs the same manual, low-value steps

Branch creation

Copy the ticket key and title from Jira, hand-format a branch name, hope it matches team convention.

Commit messages

Manually type conventional-commit prefixes and re-type the ticket key every time.

Push + merge request

Push, open GitLab, create the MR, write a description, remember to link the ticket.

Ticket status

Switch back to Jira and move the ticket to In Progress / In Review — frequently forgotten.

The cost: wasted time and context-switching across three tools for purely mechanical work; inconsistent naming that weakens code↔ticket traceability; stale Jira boards because status updates depend on memory; and thin MR descriptions that slow reviewers down. None of it is hard — it's friction, repeated all day, that adds up across the team.
3 · Proposed solution

Two commands and a sidebar collapse the whole loop

1

Create Branch from Jira Ticket

Pick from your active-sprint tickets in the sidebar or a quick-pick — no typing keys from memory. Loopline generates a convention-correct branch like bugfix/LPB-1234-login-fails, optionally fetches the base branch first, checks it out, opens the ticket description alongside your editor, and can move the ticket to In Progress.

2

Commit, Push & Create MR

Loopline reads the ticket key back out of the branch name, builds a conventional commit (feat: LPB-1234 …), pushes with upstream tracking, opens a GitLab MR with an auto-generated description, and can move the ticket to In Review.

Everything conventional is enforced by default and configurable per team — including, since v0.21.0, via a single committed .loopline.json.

4 · What's built — core workflow & sidebar

Prototype v0.24.9

Loopline sidebar

Dedicated activity-bar panel: current branch/ticket, active-sprint tickets grouped by status (In Progress expanded by default), color-coded icons by issue type. Click to branch, open in Jira, or jump back to main/master in one click when the tree is clean.

Branch creation

Issue-type→prefix mapping, confirm/edit, existing-branch guard (check out / rename / cancel), optional fetch of a fresh base branch first.

Commit, push & MR

Duplicate-MR detection, automatic GitLab project detection from the git remote, staging that respects what you've already staged.

4 · What's built — AI capabilities (all opt-in)

Optional, reviewable, and now provider-flexible

AI-generated MR descriptions

Drafts a Summary / Changes / Why / Testing body from the diff and ticket — reviewed and edited by you before it posts. Falls back to a deterministic file-list description if disabled.

AI implementation suggestions

After a branch is created, drafts a starting plan (goal, likely areas to change, edge cases, tests, open questions) grounded in the ticket and repo layout.

Acceptance-criteria coverage check

Before the commit, asks whether the diff addresses what the ticket requires. Silent when complete; pauses with "Commit anyway / Cancel" otherwise. Fails open on any error.

Standup summary generatorNew

Discovers every git repo in the workspace, groups today's commits by repo then ticket, and rephrases each into one grounded line — or a plain bulleted list with AI off. Opens in a themed, copy-to-clipboard panel.

Dual AI providerNew

Anthropic Messages API, or an OpenAI-compatible internal gateway (e.g. Bedrock behind a corporate proxy) — one setting, same feature set, same review-before-send model.

Auto-drafted changelogNew

No AI involved: creating an MR can draft a bullet into CHANGELOG.md from the ticket key and commit summary, filed under the right section by branch prefix.

AI-ready ticket contextNew

Copy AI context builds grounded Markdown from the ticket — summary, parsed acceptance criteria/constraints, open questions, repo layout — to paste straight into Claude Code or Copilot Chat.

Optional CLAUDE.md syncNew

Opt-in setting writes that same context into a delimited block in CLAUDE.md automatically after branch creation, or on demand — so Claude Code picks it up without a manual copy/paste.

4 · What's built — reliability, connectivity & team config

Built to survive a real corporate network

Proxy support

HTTPS_PROXY/HTTP_PROXY/NO_PROXY, plus an explicit override — since Node doesn't inherit the OS proxy.

Corporate CA support

Trusts private/corporate CAs for self-hosted Jira/GitLab behind an inspecting proxy, with a clearly-marked, discouraged insecure-TLS escape hatch.

Diagnose Connection

One-click report: versions, proxy config, loaded CAs, DNS, and a live authenticated call to each service with the precise failure code. Tokens never logged.

Branch/commit templatesNew

Token-based templates reshape generated names per team, defaulting to today's exact format so nothing changes unless edited.

.loopline.jsonNew

One committed config file standardizes conventions for the whole team on clone — read-only unless scaffolded explicitly, never secrets.

Guided setup wizard

Live credential validation for Jira, GitLab, and the chosen AI provider. All secrets in VS Code Secret Storage — never in settings files.

Per-repo git flagsNew

loopline.git.commitExtraArgs / pushExtraArgs pass extra flags (e.g. --no-verify) to every commit/push, set in a repo's own workspace settings so it never leaks to other repos.

CI-published to the MarketplaceNew

A GitLab CI stage publishes to the VS Code Marketplace automatically on every version bump to main, via a CI-scoped token — no local publish step.

6 · Security & privacy

Off by default, reviewable, and locally scoped

Secret Storage only

Jira token, GitLab token, and the chosen AI provider's key all live in VS Code Secret Storage — never in settings.json or source control.

AI is opt-in, reviewed before send

All four AI features are off by default. When enabled, they send the diff and ticket text to Anthropic or an internal OpenAI-compatible gateway — your choice, with a configurable base URL for routing through a company gateway.

Everything else works without AI

If AI is disabled, branch creation, commits, MRs, and status transitions are unaffected.

No telemetry

Impact counts are stored locally only, in VS Code's own state store. Nothing is transmitted anywhere — including to us.

This is the main area for a policy decision before enabling AI features team-wide — see §10, The ask.

8–9 · Effort, cost & risk

Low ongoing burden, well-understood risks

The prototype is delivered and de-risked further with each release. Marketplace publishing (roadmap #1) now ships itself via CI; what's left of rollout is internal registry/distribution decisions, not engineering. Later items are self-contained increments, estimable once scope is agreed. The codebase is modular and covered by 521 tests under CI, so additions stay low-risk. AI usage cost is usage-based per call and can be capped; a Sonnet-class model is inexpensive at this scale.

Third-party API changes

Jira/GitLab are already supported with graceful fallbacks (Cloud vs Server, sprint-unsupported); changes are typically small, contained fixes.

Sending code to external AI

Off by default, opt-in, configurable gateway/endpoint; can remain disabled entirely.

Adoption / "another tool"

Lives in the existing editor with a visible sidebar; a two-week pilot with one squad validates before wider rollout.

Key management

Secret Storage only; no secrets in files or repos.

Bus factor / maintenance

521 tests, CI-backed, documented codebase; low ongoing burden.
